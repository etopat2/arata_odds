# Arata Odds security controls

The app protects account data at the API and database layers. Every research endpoint except health, support contacts, and the public presentation-policy read requires a valid server-side session. Admin operations require an administrator session; account changes, backup import, and settings writes are checked on the server. Database inputs are bound parameters, and the few dynamic table names are fixed allowlists. Cross-origin mutations are rejected by Origin and Fetch Metadata checks. Sensitive API responses are not cached.

Sessions use a random 256-bit cookie token, store only its SHA-256 digest, and have HttpOnly, SameSite=Lax and HTTPS-only Secure attributes. Sessions expire after an admin-configured idle period and absolute lifetime. The admin can set a default concurrent-session limit of 1–5, override it for an account, choose to replace the oldest session or deny a new login, inspect sessions, and revoke them. Password changes and administrator resets revoke all sessions. A role, email, or activation change revokes affected sessions. New accounts and resets receive unique random temporary passwords; users must replace them at first sign-in. New PBKDF2-SHA256 hashes use the hosted runtime's supported 100,000-iteration limit. Existing compatible hashes are upgraded after a successful login; higher-iteration local hashes remain verifiable in runtimes that support them.

The hosted site sends a Content Security Policy, clickjacking and MIME-sniffing protections, a restrictive Permissions Policy, no-referrer policy, and HSTS over HTTPS. The login endpoint limits failed attempts by identity plus IP and by IP. Selected read-heavy endpoints have per-account request budgets; normal live polling is separate. These controls reduce automated harvesting and abuse, but no public web app can make already-rendered data or client-side JavaScript secret.

Admin **Security controls** also provide best-effort browser interaction switches for context menus, copying and selection, pasting, printing, common developer-tools and save shortcuts, common screenshot keys, and an account watermark. These are deterrents only. A browser user can disable JavaScript, use another browser tool or operating-system screenshot feature, inspect network traffic, or save assets that must be delivered to render the app. Blocking paste may harm password managers and accessibility, so it starts off. No setting claims to prevent every screenshot, page download, developer-tools session, scraper, or attack.

For deployment, use a unique bootstrap administrator secret, keep the site and database credentials private, apply every D1 migration, use HTTPS, review accounts and sessions regularly, and rotate credentials after suspected compromise. Browser restrictions do not replace access control or security updates.
